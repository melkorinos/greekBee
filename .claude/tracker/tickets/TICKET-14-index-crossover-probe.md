## Why

`ISSUE-01` §2 and §3 both reserve the same kind of work, and both have been carried on structural
arguments rather than numbers:

- **§2** asks whether `resolveProfiles()`'s `in()` over device UUIDs and `/api/auth/link`'s
  `auth_user_id` lookup flip to index scans at launch scale. At 47 rows the planner correctly prefers
  a sequential scan, so the existing unique indexes have never been *proven* —
  `player_profiles_auth_user_id_key` has **zero** lifetime scans.
- **§3** asks whether the nominations lookup needs an index at all. `nominations` has exactly two
  indexes — the PK and the partial unique on `(word, direction) WHERE status='pending'` — so the
  `rejected` and `accepted` count queries in
  [`src/app/api/nominations/lookup/route.ts`](../../../src/app/api/nominations/lookup/route.ts) match
  **no index**, and full-scan the table on every nomination-modal open. That is the real source of
  the 4,655 sequential scans §3 currently misattributes to the listing GET.

Both are planner questions, and **a planner question needs schema and volume, not real rows** — so
this needs no dump, no `BACKUP_ARCHIVE_PASSWORD` and no `.7z`. It is deliberately *not* blocked on
`TICKET-13`, which needs real data because it hunts data-shape failures. Different question, different
input.

The stake is a decision, not a speedup: if the index earns its place it rides runbook step 5 with the
`is_perfect` DROP (the migrations folder is frozen until then), and if it does not, §3 stops carrying
a fix nobody needs.

  ```sql
  CREATE TABLE nominations (
    id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    word        text NOT NULL,
    player_name text,
    note        text,
    device_id   text NOT NULL,
    status      text NOT NULL DEFAULT 'pending',
    created_at  timestamptz NOT NULL DEFAULT now(),
    direction   text NOT NULL DEFAULT 'add',
    reviewed_at timestamptz,
    CONSTRAINT word_suggestions_direction_check CHECK (direction IN ('add','remove')),
    CONSTRAINT word_suggestions_status_check    CHECK (status IN ('pending','accepted','rejected'))
  );
  CREATE UNIQUE INDEX nominations_pending_word_direction_key
    ON nominations (word, direction) WHERE status = 'pending';

  INSERT INTO nominations (word, direction, device_id, status, note, player_name)
  SELECT 'w' || g,
         CASE WHEN g % 4 = 0 THEN 'remove' ELSE 'add' END,
         gen_random_uuid()::text,
         CASE WHEN g % 100 < 78 THEN 'rejected'
              WHEN g % 100 < 99 THEN 'accepted' ELSE 'pending' END,
         repeat('x', 40), 'name' || g
  FROM generate_series(1, :n) g;
  ANALYZE nominations;

  -- the unindexed one, run before and after the candidate index
  EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM nominations
   WHERE word = 'w1234' AND direction = 'add' AND status = 'rejected';

  -- the listing GET, which the partial index may or may not already serve
  EXPLAIN (ANALYZE, BUFFERS) SELECT id, word, player_name, note, created_at
    FROM nominations WHERE direction = 'add' AND status = 'pending'
   ORDER BY created_at DESC;

  -- the candidate
  CREATE INDEX nominations_word_direction_status_idx ON nominations (word, direction, status);
  ANALYZE nominations;
  ```

## Open questions — answer before starting, act outside this ticket

Two decisions came out of the 2026-08-16 grill and were deferred to whoever picks this up:

1. **Does the nominations moderation concern leave `ISSUE-01` §3 as its own issue?** Once retention
   is affirmed and the index has a verdict, §3's residue is a review-workflow problem — no
   bulk-reject in `/leksikastirio`, and `word`/`note` free text written by strangers rendered in an
   admin UI — which has nothing to do with the database. If yes, it becomes a new issue at the next
   free number — as of 2026-08-16 that is **ten**, with 01/03/05 on disk and 02/04/06/07/08/09 in the
   `SPENT` ledger. Deliberately not written here as a tracker id: `trackerReferences.test.ts` fails on
   a reference to a file that does not exist, and reserving a number is not a reason to create one.
2. **When does the one non-normalised row get fixed?** `ιουνιος` (`direction` `remove`, rejected
   2026-07-15) ends in a final sigma, so `normalizeLetters` turns a re-proposal into `ιουνιοσ` and
   its prior-rejection warning can never fire. It is the only such row in 191, and the blocklist does
   not cover it because `isBlockedWord` only runs on `add`. It is a data `UPDATE`, not DDL, so the
   migrations freeze does not reach it — runbook step 5, or the dashboard at any time.

## Notes for whoever picks this up

- **Local is PostgreSQL 18, hosted is 17.** This measures whether an index is *worth having* at a
  given row count — it is not a production latency claim. `TICKET-13` carries the same caveat and it
  applies here with more force, because this ticket is entirely about planner behaviour.
- `psql` prompts interactively and will hang an agent's shell. Pass the password via `PGPASSWORD` in
  the environment and use `-w`, which fails fast instead of prompting.
- Seed the 50,000-row cases before `ANALYZE`, not after — a plan chosen on stale statistics is the
  exact failure mode §2 warns about, and reproducing it here by accident would waste the run.
