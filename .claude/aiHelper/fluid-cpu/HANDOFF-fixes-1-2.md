## Item 1 — stop serializing word lists into SSR payload

Problem: [src/app/leksiarxeio/page.tsx](../../../src/app/leksiarxeio/page.tsx) and
[src/app/vres-tin-frasi/page.tsx](../../../src/app/vres-tin-frasi/page.tsx) are
`force-dynamic` and pass ~2.1 MB of word lists as props → ~2.4 MB RSC/HTML per view.

Agreed direction:
- Serve word pools from static, CDN/browser-cacheable endpoints — route handler(s)
  with `export const dynamic = "force-static"` (prerendered at build; per-length
  `[length]` param via `generateStaticParams`, lengths 2–8 from `LEKSIARXEIO.LENGTHS`
  in `src/config/gameRules.ts` — note vres-tin-frasi also needs 2 and 3).
- Client fetches once (module-level cache), builds the `Set` there.
- Wire shape today: `LeksiarxeioBoard` → `useLeksiarxeioState(puzzle, validWords)`;
  `VresTinFrasiBoard` → `useVresTinFrasiState(puzzle, validWords)`. Both build
  `Set` via `useMemo` and pass it to `SUBMIT_GUESS`.
- **Loading gate is the main edge case**: user submits before lists arrive.
  Decide + test explicitly (e.g. submit shows a transient "λεξικό φορτώνεται…"
  FeedbackBanner message, or keyboard disabled until loaded). Game logic in
  `src/games/*/lib/` stays pure — the gate lives in hooks/components.

TDD slices (suggested): ① static route handler serves correct list w/ test →
② client hook (fetch + cache + error state) w/ test → ③ leksiarxeio wiring +
loading-gate tests → ④ vres-tin-frasi wiring (combined 2–8 pool) → ⑤ delete the
server-side word-list props and their imports from both pages.

## Item 2 — daily pages: once-per-day puzzle claim + ISR

Problem: `consumeApprovedPuzzle` (`src/lib/communityPuzzleLifecycle.ts`) runs per
page view on the `force-dynamic` daily pages (`/leksiarxeio`, `/vres-tin-frasi`;
same pattern used by `src/data/{leksiarxeio,vrestifrasi}/index.ts`). Any visitor
can consume a queued community puzzle mid-day; two same-day visitors can get
different puzzles. Design decision needed (grill the user if unclear):

- Preferred shape: a `daily_puzzles` table (game_id, date, puzzle payload,
  submitter_name; unique on game_id+date). First render of a new date claims
  from the community queue (or static fallback) and inserts atomically —
  `insert … on conflict do nothing` then read back, so concurrent renders agree.
- Then pages drop `force-dynamic` → `export const revalidate = 300` (or similar).
- Watch: midnight rollover (`getTodayDateString()` is UTC; a stale cached page
  may serve yesterday's puzzle for up to `revalidate` seconds — acceptable, but
  confirm with user), leaderboard keys (`{date}-wordle-{len}`, `{date}-vresi` —
  must not change), empty-queue fallback (static rotation must still work).
- DB change = migration file in `supabase/migrations/` + `npx supabase db push`
  (no Docker needed). **One Supabase project backs dev AND prod** — every write
  is production. RLS: page render uses the anon client; the insert path needs a
  policy (check existing community-puzzle policies for the pattern).
- `/leksindeseis` + `/stavrolekso` are also `force-dynamic` but light; converting
  them is optional/follow-up (stavrolekso lists all approved puzzles — different
  freshness needs).
