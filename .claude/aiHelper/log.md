## Session 131 — 2026-07-30: Leksokipos difficulty rebalance — the soft cap WAS the unfairness (plan review → `/tdd`)

Reviewed an authored rebalance plan, found its central diagnosis inverted, then implemented the corrected fix. **The plan's own tables all reproduced exactly** (genius p50 478, words p50 84, max 128, pangram max 110) — the data was never in question, the interpretation was. **The finding that flipped it:** `frac_of_garden = wordsToGenius/n = (top% × scale × total)/(mean × n)`, and `mean × n ≡ total`, so **without softCap every puzzle demands exactly `scale × top%` of its own garden — spread 0.009, perfect fairness.** The cap is not *a* contributor to the small-vs-big unfairness, it is the *entire* source: it discounts only the ~75% of puzzles above the knee. So the plan's goal «make big puzzles harder» was aimed backwards — big puzzles were the *fair* ones being made cheap; small puzzles at 69% were the honest baseline. **Why the cap still stays:** removing it explodes tedium (words p90 68→214, max 728) and trimming to compensate keeps only 50–56% of the corpus. The cap trades fairness for a tedium ceiling and that trade is correct — the only question is where to sit on it. **The plan's recommendation was the worst config in its own family:** knee 500 / k 250 / top 75% → spread 0.312 with words p50 and max going *up* (84→86, 128→130), partly undoing the trim. The plan searched knee/k/top but never `SCORE_SCALE` — the one knob that reaches the sub-knee puzzles the cap cannot touch. **Shipped instead:** `SCORE_SCALE` 0.85→**0.75**, `SOFT_CAP_K` 250→**400**, knee 400 and the 80% rank threshold **unchanged**. Spread 0.363→0.193; %-garden small 69→61, big 33→39 (big genuinely harder, overshoot 328%→259%); words p50 84→71, max 128→106. **Leaving the rank threshold alone is load-bearing:** `leksokipos-stin-korifi` fires on `rank === TOP_RANK` and achievement ids are FROZEN on first deploy — moving 80→75 would silently redefine an earned badge forever. (`theristisFoundRatio: 0.8` is an unrelated 80% — do not "sync" them.) **Corpus:** new `scripts/lib/leksokipos/puzzleQuality.ts` (imports the real `scoreWord`/`softCap`/`isPangram` — never reimplements; a parity test pins it to `maxScore`) + `prune-leksokipos-puzzles.ts` → **1008→799**, removed 209 (170 tedium-only, 9 pangram-only, 30 both), dates reflowed 2026-03-25→2028-05-31 (~2.19 yr). Operator chose gate 107 over 115/125 after a runway sweep. **Both gates earn their keep** — measured on the pre-trim corpus, 19 boards failed ONLY the pangram rule, so it is not redundant with tedium. **The gate count moved 153→209 because the plan measured the 107-word gate under the OLD config**; measuring it under the new one is self-consistent but stricter (~7 months of runway). **Generators taught the gates** (batch REJECTS and releases the consumed date via `usedSets.delete` + `dayOffset--`; generate-puzzle WARNS since the caller picks letters deliberately) — without this the next batch reintroduces exactly what was deleted. **Two legacy tests were genuinely invalidated, not fudged:** `gameLogic` maxScore 34→30, and a GameBoard fixture whose 22-pt "below top rank" case became 88% under the new scale (swapped to a 16-pt set = 64%). **The reflow retired `everyPuzzleHasPangram`'s two-board legacy exemption** — those dates now hold different puzzles, both with pangrams, so the allowlist was deleted and the invariant made unconditional rather than left as a dead exception. New guards: `puzzleQuality.test.ts` (11) + `puzzleCorpusQuality.test.ts` (quality gates + **date integrity**, mandatory because `getPuzzleForDate` falls back to the LAST puzzle on a miss — a gap would silently serve the 2028 board, never throw). Gates: 182 files / 2204 tests / eslint 0 / build 0 (prerendered params 1008→799). Branch `dev`, ready to push — **not pushed**.
