## Session 139 — 2026-08-07: `player_milestones` — one table, one route, one merge (TICKET-01, `/grill-with-docs` → `/tdd`)

The whole vertical slice: `player_pangrams` + `player_words` dropped, `player_milestones(device_uuid, puzzle_date, kind, detail, value)` created with the two day counters nothing previously captured, `POST /api/milestones` replacing two routes, `planMilestoneMerge` replacing two planners, and a fifth sync lane. Migration `20260807120000` is **committed and NOT pushed** — one Supabase project backs dev and prod, so the drop is live on push; run `npx supabase db push` and the Vercel deploy back to back, after hours.

**The grill found two things the ticket had wrong, and both changed the build.** First, the ticket justified the cold drop with "the beta word capture is dark behind `FEATURE_FLAGS.achievements`" — that flag has been `true` since s112. The capture is live; the drop is fine anyway (no `player_achievements` row depends on those rows, so nothing is un-earned — only progress bars restart), but the stated reason was false and the operator decided the drop knowingly rather than on a wrong premise. Second, and this is the durable one: **`theristisFoundRatio` had to move 0.8 → 0.7 in THIS ticket, not TICKET-02.** Milestone rows are only written as days are played, so every qualifying day between now and the catalog rebuild would have been permanently unrecorded. Lowering is the safe direction anyway. The same reasoning made `value` carry the achieved percentage on `tzimani` rows — the spec had recorded that calibration signal as deliberately forgone, but forgoing it only cost something while it needed its own row; on a row already being written it is free. It captures the distribution *above* the threshold only, and the operator accepted the near-miss blind spot explicitly.

Operator also settled: pure plumbing (no catalog id or threshold moves — those stay TICKET-02's), and counts returned only for kinds that actually inserted. That last one is the load-bearing cost fix, together with **filtering words to ≥10 client-side**: the lane fired per found word and the server dropped almost all of them, ~20–40 requests a game writing nothing. Measured from the beta — 104 word rows over ~365 player-days — a qualifying find happens about once every three or four days, so the lane went from ~30 requests a game to under 4 a *day* across all four kinds. `.select("kind")` after the upsert is what makes both rules work: `ON CONFLICT DO NOTHING ... RETURNING` yields only genuinely-new rows, so the returned kinds are exactly the totals that moved, and an empty result skips the aggregate outright.

Nine TDD slices, red before green on each. New pure seams: `planMilestoneMerge` (8 tests), `sanitizeMilestones` (16, per-kind dispatch), `detectDayMilestones` (9). Routes: `milestonesRoute` (14). One self-inflicted red worth recording — the hook test asserted TICKET-02's pangram thresholds (25/60/150) against the shipped ones (10/20/50); fixed by deriving from `achievementTuning` rather than hardcoding, since these are lane-behaviour tests, not boundary tests. `.next` needed clearing once: the generated route validator still referenced the deleted `/api/pangrams`.
