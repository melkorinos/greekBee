1 — Score Submission: Three Shallow Hooks, Two Endpoints

src/hooks/useScoreSubmission.ts · useLeksiarxeioScoreSubmission.ts · useLeksindeseisScoreSubmission.ts · useScorePost.ts

Strong

Three hooks post scores to the server. They share the same structure — get deviceId, guard against empty payload, fire-and-forget POST — but each reinvents the plumbing independently. useScorePost was meant to be a shared base but it's a pass-through: it adds one ref-update pattern around a single postScore() call, so its interface is nearly as complex as its implementation. Deletion test: remove useScorePost — complexity reappears inline in three callers. Keep it, but make it earn its depth.

What changes

  • One useScoreSubmission(config) hook replaces all three; game-specific payload fields live in a config object.
  • Unify /api/game-scores + /api/leksiarxeio-scores into a single /api/scores route; penalty logic (won ? attempts : 7) moves server-side where it belongs.
  • useScorePost becomes the single base — or disappears if the new hook inlines the ref pattern directly.

Benefits — locality & leverage

Locality: changes to score-posting (adding a field, changing auth, rate-limiting) happen in one file. Today they must be replicated across three. Leverage: callers pass a config object; the hook owns retry, dedup, ref-stability, and display-name injection. Tests assert the payload shape once.

Server-side prerequisite: the endpoint unification requires a small API route migration. The client refactor can precede this by keeping the old endpoints temporarily, but the full gain requires both.

2 — Device Identity: Leksiarxeio Diverges From the Platform Envelope

src/components/leksiarxeio/LeksiarxeioBoard.tsx · src/hooks/useGameStore.ts · src/types/index.ts

Strong

Leksokipos and Leksindeseis share one deviceId through the unified wordgames:state persistence envelope. Leksiarxeio hard-codes its own "leksiarxeio-identity" slice and runs a private getOrCreateDeviceId() inside the board component — three functions from the ground up, invisible to the platform's identity layer. The same player therefore has two different device IDs depending on which game they play.

BEFORE — split identity

// LeksiarxeioBoard.tsx (lines 30-36)
function getOrCreateDeviceId() {
  const existing = readSlice("leksiarxeio-identity");
  if (existing?.deviceId) return existing.deviceId;
  const id = crypto.randomUUID();
  writeSlice("leksiarxeio-identity", { deviceId: id });
  return id;
}

Component writes directly to the persistence envelope. Duplicates logic in useGameStore.

AFTER — unified identity

// LeksiarxeioBoard.tsx
const deviceId = useGameStore(s => s.deviceId);

// useGameStore.ts already provides getOrCreateDeviceId()
// The "leksiarxeio-identity" slice is removed.
// PersistenceEnvelope loses the extra key.

One device identity across all games. Leaderboard cross-game player matching works.

Benefits

Locality: device identity logic lives once, in useGameStore. Leverage: a future "player stats across all games" feature is trivially possible — today it would see two unrelated players. The PersistenceEnvelope type loses an opaque "leksiarxeio-identity"? key.

Migration note: existing Leksiarxeio players have a leksiarxeio-identity slice. On first load after the refactor, useGameStore's envelope should check for the old key and migrate the ID rather than generating a new one — otherwise leaderboard history disconnects.

4 — Leksindeseis Shuffle: State Split Across Reducer and useState

src/games/leksindeseis/hooks/useLeksindeseisState.ts · leksindeseisReducer.ts

Worth exploring

The Leksindeseis state hook stores shuffleOrder in a standalone useState (line 65) rather than in the reducer. The stated reason in a comment: "displayOrder derives from it by filtering out solved words — no setState in effects." This is a clean implementation, but it means the full visual game state requires two sources of truth: the reducer for game logic, and useState for display order. The SHUFFLE action in the reducer is a no-op (return { ...state }) that signals the hook to call setShuffleOrder.

BEFORE — split state

// useLeksindeseisState.ts
const [state, dispatch] = useReducer(...)
// shuffleOrder lives OUTSIDE the reducer:
const [shuffleOrder, setShuffleOrder] = useState(allWords)

// Reducer SHUFFLE action:
case "SHUFFLE":
  return { ...state }  // ← no-op, hook responds

AFTER — unified state

// leksindeseisReducer.ts
case "SHUFFLE":
  return { ...state, shuffleOrder: shuffle(state.shuffleOrder) }

case "SUBMIT_GUESS":
  // When a group is solved, filter it from shuffleOrder
  return { ...state, solvedGroups: [...], shuffleOrder: remaining }

Benefits

Locality: all game state changes happen in one place (the reducer), making the hook a thin wrapper. Testability: the current split means SHUFFLE can't be tested through the reducer alone — the hook's useState response is invisible to reducer tests. Unifying it makes shuffle behavior directly testable in leksindeseisReducer.test.ts.

Low risk: this is a refactor inside a single hook and its reducer. No public API changes. The test suite already has leksindeseisReducer.test.ts with full coverage — the shuffle tests would move from a hook test to a reducer test.

5 — Scoring Calculation: Reducer-Owned vs. Hook-Derived

src/games/leksokipos/hooks/gameReducer.ts · src/games/leksiarxeio/hooks/useLeksiarxeioState.ts

Speculative

Leksokipos accumulates score inside the reducer as part of game state — every SUBMIT_WORD action updates state.score. Leksiarxeio derives its score in the hook via useMemo after the game ends. Both are valid patterns, but they mean the two games answer "what is the current score?" from different layers. This is a minor inconsistency — neither approach is wrong — but it's worth noting as the platform grows.

Leksokipos — score in reducer

// gameReducer.ts line 91
case "SUBMIT_WORD":
  const pts = scoreWord(word, puzzle);
  return { ...state, score: state.score + pts, ... }

Leksiarxeio — score in hook (useMemo)

// useLeksiarxeioState.ts line 84
const score = useMemo(() =>
  state.status !== "playing"
    ? scoreLeksiarxeio(state.guesses.length, state.status === "won")
    : 0,
  [state.guesses.length, state.status]
);

Leksiarxeio's score is a pure function of end-game state (attempt count + won/lost), so deriving it with useMemo is correct. The inconsistency is cosmetic unless you want a unified "how do I find the score?" rule across all games. Recommendation: leave as-is unless a third game introduces a third pattern.

Speculative: Only worth addressing if a new game creates a third scoring pattern, or if a unified "game score API" is needed. Don't fix this speculatively.
