Architecture Review

Greek Word Games Platform · 2026-05-26

Strong Worth exploring Speculative

Four candidates surfaced by reading the codebase. Game library modules (src/games/*/lib/) are deep and well-tested — no friction there. The friction lives in the glue layer: the three GameBoard components and the score-submission hooks.

Candidate 1

Score Submission Hooks

Strong

Files

  • src/hooks/useScoreSubmission.ts
  • src/hooks/useLeksiarxeioScoreSubmission.ts
  • src/test/shared/useScoreSubmission.test.ts
  • src/test/leksindeseis/useLeksindeseisScoreSubmission.test.ts

Problem

Two hooks implement nearly the same protocol (dedup guard, displayName ref, POST, error silencing) but diverge only on endpoint and one penalty-mapping rule. Callers must choose which hook to use with no guiding abstraction. Test suites are near-duplicates.

Deletion test

Delete both hooks → the dedup guard ("only POST when score strictly increases") and the displayName ref pattern reappear in each GameBoard. Complexity concentrates — these hooks have real depth. The divergence is shallow enough to unify.

Before

GameBoard → useScoreSubmission (Leksokipos + Leksindeseis)
LeksiarxeioBoard → useLeksiarxeioScoreSubmission (Leksiarxeio only)
ConnectionsBoard → useScoreSubmission (re-used, leaks game-specific param)
✗ Callers choose the hook. Nearly-identical test files. Penalty logic lives inside the hook it belongs to, not discoverable.

After

useScoreSubmission(gameId)
↳ shared: dedup guard
↳ shared: displayName ref
↳ adapter: leksarxeio penalty
✓ One hook, one test file. Adapters plug in game-specific transforms. Callers pass gameId, not a different import.

Solution

Merge both hooks into a single useScoreSubmission(gameId, ...). The shared core handles dedup, displayName ref, fetch, and error silencing. A small game adapter table maps each gameId to its endpoint and any pre-submit transform (e.g. Leksiarxeio's failed → 7 penalty). One test file exercises core + both adapters.

Benefits

  • Locality: the dedup invariant lives in one place — one edit, all games benefit.
  • Leverage: adding a fourth game means adding one adapter entry, not a new hook.
  • Tests: one test file instead of two near-identical ones; adapter tests are additive.
Candidate 2

GameBoard Identity Initialisation

Strong

Files

  • src/components/leksokipos/GameBoard.tsx
  • src/components/leksiarxeio/LeksiarxeioBoard.tsx
  • src/components/leksindeseis/ConnectionsBoard.tsx

Problem

All three boards initialise DeviceId and DisplayName on mount — but two use a reducer and one uses useState. This is the same concern resolved three different ways. Any future change (e.g., SSR fix, new field) must be applied in three places.

Deletion test

Delete the identity initialisation from all three boards → the SSR guard (typeof window === "undefined") and the getOrCreateDeviceId() call reappear in each. Not complex per-instance, but the inconsistency means bugs fixed in one board silently persist in the others.

Before — 3 different patterns

// GameBoard.tsx (useState)
const [displayName, setDN] = useState(
  () => typeof window === "undefined"
    ? "" : getDisplayName()
);
const [deviceId, setDId] = useState(
  () => typeof window === "undefined"
    ? "" : getOrCreateDeviceId()
);

// LeksiarxeioBoard.tsx (reducer)
const [identity, dispatch] = useReducer(
  identityReducer, { deviceId:"", displayName:"" }
);
useEffect(() => {
  dispatch({ type:"INIT",
    deviceId: getOrCreateDeviceId(),
    displayName: getDisplayName() });
}, []);

// ConnectionsBoard.tsx (reducer — same as above)
const [identity, dispatch] = useReducer(
  identityReducer, { deviceId:"", displayName:"" }
);
useEffect(() => {
  dispatch({ type:"INIT", ... });
}, []);

After — one hook

// src/hooks/useGameIdentity.ts
export function useGameIdentity() {
  const [deviceId, setDeviceId] = useState(
    () => typeof window === "undefined"
      ? "" : getOrCreateDeviceId()
  );
  const [displayName, setDisplayName] = useState(
    () => typeof window === "undefined"
      ? "" : getDisplayName()
  );
  return { deviceId, displayName,
           setDeviceId, setDisplayName };
}

// All three boards:
const { deviceId, displayName,
        setDeviceId, setDisplayName }
  = useGameIdentity();

Solution

Extract a useGameIdentity() hook that owns the SSR-safe init pattern and returns { deviceId, displayName, setDeviceId, setDisplayName }. All three boards call it. The reducer variant can be deleted.

Benefits

  • Locality: one place to fix SSR bugs or add a new identity field.
  • Leverage: the hook is small (20 lines) but eliminates 60 lines of scattered duplication.
  • Tests: useGameIdentity.test.ts can cover the SSR path once and for all.
Candidate 3

GameBoard Shell — Leaderboard & Score Wiring

Worth exploring

Files

  • src/components/leksokipos/GameBoard.tsx
  • src/components/leksiarxeio/LeksiarxeioBoard.tsx
  • src/components/leksindeseis/ConnectionsBoard.tsx

Problem

All three boards wire up: (1) identity init, (2) score submission hook, (3) auto-post effect, (4) leaderboard modal open/close state, (5) 🏆 button visibility rule (daily puzzle only). This is ~50 lines of identical structure per board.

Deletion test

Delete the shared boilerplate → it reappears in all three boards. However, each board has enough game-specific divergence (Leksokipos has sync + verification; Leksiarxeio has 5 length panels) that a full shell component risks becoming a leaky abstraction.

Before — duplicated shell concern

GameBoard.tsx

useScoreSubmission(...)

useEffect → postScore

isLeaderboardOpen state

isDaily check → 🏆 visibility

+ useProfileVerification (only here)

+ useGameStateSync (only here)

LeksiarxeioBoard.tsx

useGameIdentity (reducer form)

useLeksiarxeioScoreSubmission(...)

useEffect → postScore

isLeaderboardOpen state

isDaily check → 🏆 visibility

ConnectionsBoard.tsx

useGameIdentity (reducer form)

useScoreSubmission(...)

useEffect → postScore

isLeaderboardOpen state

isDaily check → 🏆 visibility

After — hook extracts shared concern

useGameShell({ gameId, score, puzzleDate, isDaily })

Returns: identity, postScore, submitWithName,

isLeaderboardOpen, openLeaderboard, closeLeaderboard

GameBoard.tsx

const shell = useGameShell(...)

+ useProfileVerification (opt-in)

+ useGameStateSync (opt-in)

LeksiarxeioBoard.tsx

const shell = useGameShell(...)

ConnectionsBoard.tsx

const shell = useGameShell(...)

Solution

Extract useGameShell({ gameId, score, puzzleDate, isDaily }) that wires identity + score submission + leaderboard state. Each board calls it and unpacks what it needs. Game-specific hooks (useProfileVerification, useGameStateSync) remain opt-in per board — they are not swallowed by the shell.

Benefits

  • Locality: the "daily puzzle → show 🏆" rule lives in one place.
  • Leverage: a fourth game gets all platform plumbing from one hook call.
  • Tests: useGameShell.test.ts covers leaderboard open/close + score post once.
Note: Candidate 1 (unify score submission) and Candidate 2 (useGameIdentity) should land first — useGameShell composes them.
Candidate 4

useProfileVerification & useGameStateSync — Leksokipos-only Leak

Speculative

Files

  • src/hooks/useProfileVerification.ts
  • src/hooks/useGameStateSync.ts
  • src/components/leksokipos/GameBoard.tsx

Problem

Cross-device profile verification (silently disconnect on 404) and game state sync (push foundWords to server) are only wired into Leksokipos. Leksiarxeio and Leksindeseis don't verify profile staleness — a stale profile is never caught until the player loads Leksokipos. Neither hook has test coverage.

Deletion test

Delete both hooks — no other file imports them. This is a sign they're not earning their place as platform abstractions; they are game-specific utilities that incidentally live in src/hooks/.

GameBoard (Leksokipos)
useProfileVerification ✓
useGameStateSync ✓
LeksiarxeioBoard
useProfileVerification ✗
useGameStateSync ✗
ConnectionsBoard
useProfileVerification ✗
useGameStateSync ✗

A stale cross-device profile is never detected if the player only opens Leksiarxeio or Leksindeseis.

Two options

  1. Promote to platform: move profile verification into useGameShell (Candidate 3) so every game checks it on mount.
  2. Document as intentional: if cross-device sync is Leksokipos-only by product decision, record it as an ADR so future reviews don't re-raise it.

Why speculative

This may be a deliberate product decision (only Leksokipos has sync), not accidental friction. Needs a conversation with the maintainer before acting. Either outcome (promote or ADR) is valid.

Top recommendation

Candidate 2 first, then Candidate 1. Start with useGameIdentity() — it is the smallest, most self-contained deepening (20 lines, one new test file, immediate consistency win across all three boards). Once that lands, unify the score submission hooks (Candidate 1): the dedup guard and displayName ref pattern are the right things to protect, and having a single hook makes Candidate 3 (the shell) a natural next step.

  1. useGameIdentity() — extract, test, replace 3 copy-paste patterns
  2. useScoreSubmission(gameId) — unify, delete useLeksiarxeioScoreSubmission, merge test files
  3. useGameShell() — compose the above, test leaderboard + auto-post once
  4. Candidate 4 — decide: promote profile verification or write an ADR
