Architectural Friction Report

Five deepening opportunities found by exploring the codebase organically. Each candidate is evaluated using the deletion test: would removing the module concentrate complexity, or just move it? Diagrams use domain vocabulary from CONTEXT.md and architecture vocabulary from LANGUAGE.md.

Candidate 1

Three nearly-identical Score submission hooks

Strong

Files

src/hooks/useScoreSubmission.ts src/hooks/useLeksiarxeioScoreSubmission.ts src/hooks/useLeksindeseisScoreSubmission.ts

Problem

All three hooks share an identical structure: a displayNameRef for stale-closure avoidance, a useEffect that fires on score change, a deviceId guard, and a fire-and-forget POST. The differences are surface-level: endpoint URL, field names, and whether a loss maps to a penalty score. This is a shallow interface repeated three times — the deletion test confirms it: deleting any one hook doesn't concentrate complexity, it just moves it to a caller. That's the signal of a pass-through.

Real risk: a bug in the stale-closure pattern (already subtle) must be fixed in three places independently.

Solution

Extract a single useScoreSubmission(config) hook. The config object supplies the endpoint, field mapping, and optional penalty transform. Each game creates its own thin adapter that passes a config — not 85 lines of logic, just a config literal. The seam is now the config interface; each game is an adapter at that seam.

Before — three parallel implementations

// useScoreSubmission.ts (~85 lines)
const ref = useRef(displayName);
useEffect(() => { ref.current = displayName }, [displayName]);
useEffect(() => {
  if (!deviceId || !enabled) return;
  fetch('/api/scores', { method:'POST',
    body: JSON.stringify({ device_uuid: deviceId,
      display_name: ref.current, score, puzzleId }) });
}, [score, deviceId, enabled]);

// useLeksiarxeioScoreSubmission.ts (~85 lines)
const ref = useRef(displayName);  // ← copy-paste
useEffect(() => { ref.current = displayName }, [displayName]);
useEffect(() => {
  if (!deviceId || !enabled) return;
  const attempts = won ? guessCount : 7;  // ← only real diff
  fetch('/api/scores/leksiarxeio', { ... });
}, [guessCount, won, deviceId, enabled]);

// useLeksindeseisScoreSubmission.ts (~85 lines)
const ref = useRef(displayName); // ← copy-paste again
...

After — one deep module, three adapters

// useScoreSubmission.ts (deep, ~60 lines)
export function useScoreSubmission<T>(config: {
  endpoint: string;
  buildPayload: (ctx: SubmitCtx) => T;
  trigger: unknown;   // the value that fires submission
  enabled: boolean;
}) { /* stale-ref + fetch, once */ }

// useLeksokiposScoreSubmission.ts (~12 lines)
export function useLeksokiposScoreSubmission(...) {
  return useScoreSubmission({
    endpoint: '/api/scores',
    buildPayload: (ctx) => ({ score: ctx.score, ... }),
    trigger: score,
    enabled,
  });
}

// useLeksiarxeioScoreSubmission.ts (~12 lines)
// Only difference: penalty mapping lives here, visibly

Benefits — Locality & Leverage

  • Locality: the stale-closure fix, retry logic, or error silencing lives in one file. Any bug in the submission pattern is fixed once.
  • Leverage: callers only supply a config — they get the entire submission lifecycle (guards, ref pattern, fire-and-forget) for free.
  • Testability: the config interface becomes the test surface. You can test the generic hook with a mock config, and test each game's config literal in isolation.

Candidate 2

Leksindeseis has no pure-function lib/ folder

Strong

Files

src/games/leksindeseis/hooks/leksindeseisReducer.ts src/games/leksindeseis/types.ts

Problem

Leksokipos and Leksiarxeio both have a lib/ folder with pure functions that are tested independently. Leksindeseis has none — its two core rules (matchesGroup() and isOneAway()) are buried inside the reducer at lines 13 and 20. This is a shallow reducer: the interface (dispatch an action) is as complex as the implementation (the two rules), because you can't reach the rules without dispatching.

Deletion test on the reducer: delete it and the rules reappear as free functions in lib/ — complexity is concentrated, not moved. The reducer was earning its keep before; now we see it was also hiding something.

Solution

Extract matchesGroup(selection, group) and isOneAway(selection, group) to src/games/leksindeseis/lib/matching.ts. The reducer becomes a thin orchestrator. Both functions are now independently testable — no mock store, no dispatch, no hook setup.

Before — rules embedded in reducer

// leksindeseisReducer.ts (145 lines)

// Lines 13-19: pure logic, but unreachable
function matchesGroup(sel: string[], g: Group) {
  return sel.length === 4 &&
    g.words.every(w => sel.includes(w));
}
// Lines 20-26: pure logic, but unreachable
function isOneAway(sel: string[], g: Group) {
  const matches = sel.filter(w => g.words.includes(w));
  return matches.length === 3;
}

// Lines 80-120: reducer dispatches that call them
case 'SUBMIT_GUESS':
  const correct = state.groups.find(g =>
    matchesGroup(action.selection, g));
  ...

After — pure lib exposed at seam

// src/games/leksindeseis/lib/matching.ts
export function matchesGroup(
  selection: string[], group: Group
): boolean {
  return selection.length === 4 &&
    group.words.every(w => selection.includes(w));
}
export function isOneAway(
  selection: string[], group: Group
): boolean {
  return selection.filter(w =>
    group.words.includes(w)).length === 3;
}

// leksindeseisReducer.ts (now ~80 lines)
import { matchesGroup, isOneAway } from '../lib/matching';
// reducer is an orchestrator, not a rule-holder

Benefits — Locality & Leverage

  • Locality: matching rules (the core of Leksindeseis) live in one file. A future "hint" feature can call isOneAway() without touching the reducer.
  • Leverage: tests for the rules don't need a store, a dispatch, or a full puzzle — just two arrays.
  • Consistency: all three games now follow the same pattern (lib/ = pure rules, hooks/ = orchestration). An agent onboarding later won't have to ask "why is Leksindeseis different?"

Candidate 3

No Game Registry — GameId type and Shell nav diverge silently

Worth exploring

Files

src/types/index.ts src/components/shared/Shell.tsx src/app/page.tsx (picker)

Problem

"What games exist on the Platform?" has three separate answers in the codebase: the GameId union type in src/types/index.ts, the hardcoded GAMES array in Shell.tsx, and the picker cards in src/app/page.tsx. These three are not connected by any shared module — they are maintained by convention alone.

When a fourth Game is added, a developer must update all three independently. There is no compiler error if one is missed. The Shell may silently omit a game from the drawer; the picker may show it without a nav link.

Solution

Create src/config/games.ts — a single Game Registry that maps each GameId to its display label, href, and description. The GameId union type is derived from the registry's keys (no drift possible). Shell and picker both consume the registry. The registry becomes the seam; Shell and picker are adapters.

Before — three copies of "what games exist"

GameId union] -.->|convention| S[Shell.tsx
GAMES array] T -.->|convention| P[app/page.tsx
picker cards] S -.->|no link| P style T fill:#fee2e2,stroke:#fca5a5 style S fill:#fee2e2,stroke:#fca5a5 style P fill:#fee2e2,stroke:#fca5a5

After — one registry, two adapters

graph TD R[config/games.ts
GAME_REGISTRY] -->|derives| T[types/index.ts
GameId = keyof registry] R -->|consumed by| S[Shell.tsx] R -->|consumed by| P[app/page.tsx] style R fill:#dcfce7,stroke:#86efac style T fill:#f0fdf4,stroke:#bbf7d0 style S fill:#f0fdf4,stroke:#bbf7d0 style P fill:#f0fdf4,stroke:#bbf7d0

Benefits — Locality & Leverage

  • Locality: adding a fourth Game requires one change in one file — all consumers update for free.
  • Leverage: the registry can grow to include metadata (icon, description, color, feature flags) without touching Shell or the picker.
  • Testability: a test can assert that every entry in GAME_REGISTRY has a matching route directory, closing the gap between type-system and filesystem.

Candidate 4

Round Snapshot types defined inconsistently across games

Worth exploring

Files

src/games/leksokipos/hooks/useGameState.ts src/games/leksiarxeio/hooks/useLeksiarxeioState.ts src/games/leksindeseis/types.ts

Problem

A Round Snapshot is the typed shape of what crosses the persistence boundary — what leaves the game's Session, enters useGameStore, and survives a browser refresh. This is the most important type boundary in the system. Yet each game defines it differently: Leksokipos and Leksiarxeio define their Snapshot types inside hook files; Leksindeseis defines its in types.ts. Nobody looking at src/games/leksindeseis/types.ts would guess that the equivalent Leksokipos type is hidden inside a hook.

The PersistenceEnvelope (root types) uses unknown for each game slice — intentional — but this means TypeScript cannot cross-check the snapshot against what the envelope actually stores. The types exist, just not where a future agent would look.

Solution

Move each game's Snapshot type to its own src/games/{game}/types.ts. This makes types.ts the definitive answer to "what shape does this game persist?" — a single file, one place to look. No logic changes; this is a type-only reorganization.

Before — Snapshot types scattered

// useGameState.ts (Leksokipos hook, line 15)
type LeksokiposRoundSnapshot = {
  foundWords: string[];
  score: number;
  currentInput: string;
};
// 70 lines of hook logic below...

// useLeksiarxeioState.ts (Leksiarxeio hook, line 19)
type LeksiarxeioRoundSnapshot = {
  guesses: GuessResult[];
};

// types.ts (Leksindeseis — the outlier that got it right)
export type LeksindeseisRoundSnapshot = {
  solvedGroups: string[];
  mistakesRemaining: number;
};

After — Snapshot at the types boundary

// src/games/leksokipos/types.ts
export type LeksokiposPuzzle = { ... };
export type LeksokiposRoundSnapshot = {
  foundWords: string[];
  score: number;
  currentInput: string;
};

// src/games/leksiarxeio/types.ts
export type LeksiarxeioPuzzle = { ... };
export type LeksiarxeioRoundSnapshot = {
  guesses: GuessResult[];
};

// All three games: Snapshot lives next to Puzzle type.
// One file = one boundary = one place to look.

Benefits — Locality & Leverage

  • Locality: the persistence boundary for each Game is documented in one file, alongside the Puzzle type it belongs to.
  • Leverage: a migration tool, a schema validator, or a future remote-sync feature can import all three Snapshot types without touching hook files.
  • Consistency: Leksindeseis already does this correctly — this change makes all three Games uniform.

Candidate 5

useGameStateSync is a Leksokipos hook living in shared space

Worth exploring

Files

src/hooks/useGameStateSync.ts src/components/leksokipos/GameBoard.tsx

Problem

src/hooks/ contains useGameStore (shared — correct), useRoundPersistence (shared — correct), and useGameStateSync (Leksokipos-only — misplaced). The sync hook hardcodes game_id: "leksokipos" and posts to /api/game-state. It is only ever imported by GameBoard.tsx. Its presence in shared space implies a platform utility — it isn't.

Deletion test: delete useGameStateSync from src/hooks/ — complexity reappears in src/games/leksokipos/hooks/ where it belongs. The module earns its keep, but it's in the wrong folder.

Solution

Move useGameStateSync.ts to src/games/leksokipos/hooks/useGameStateSync.ts. Update the one import in GameBoard.tsx. No logic changes — pure file-system reorganization. The seam between shared platform hooks and game-specific hooks is now enforced by folder structure.

Before — misplaced hook implies shared

src/hooks/
  useGameStore.ts        ← shared ✓
  useRoundPersistence.ts ← shared ✓
  useGameStateSync.ts    ← Leksokipos only ✗
  useLeksiarxeioScoreSubmission.ts ← Leksiarxeio only ✗
  useLeksindeseisScoreSubmission.ts ← Leksindeseis only ✗

After — folder = contract

src/hooks/
  useGameStore.ts        ← shared
  useRoundPersistence.ts ← shared

src/games/leksokipos/hooks/
  useGameState.ts
  useGameStateSync.ts    ← belongs here

src/games/leksiarxeio/hooks/

  useLeksiarxeioScoreSubmission.ts ← belongs here

src/games/leksindeseis/hooks/
  useLeksindeseisState.ts
  useLeksindeseisScoreSubmission.ts ← belongs here

Benefits — Locality & Leverage

  • Locality: everything Leksokipos-specific lives under src/games/leksokipos/. No hunting across folders to understand one game.
  • Leverage: shared hooks folder becomes a strict contract — anything in src/hooks/ is actually shared. Future agents can rely on this.
  • Testability: no change — but a future glob test can assert that src/hooks/ contains no hardcoded game IDs.

Top Recommendation

Start with Candidate 2 — Leksindeseis lib/ extraction

It is the smallest change, the clearest win, and it has zero risk: extract two small pure functions from the reducer into a new file. No API changes, no hook refactoring, no type migrations. The result is immediately testable and establishes pattern consistency across all three Games — which makes every future agent session predictably easier to navigate.

Once done, Candidate 1 (score submission hooks) is the highest leverage: ~85 lines of copy-paste code becomes ~60 lines of shared logic + ~12 lines per game. The stale-closure pattern, one of the subtlest pieces of the codebase, will be audited and fixed exactly once.

Suggested order

  1. Candidate 2 — Leksindeseis lib/ (30 min, zero risk)
  2. Candidate 1 — Score submission hooks (2–3 h, high leverage)
  3. Candidate 5 — Move game-specific hooks (15 min, file rename)
  4. Candidate 4 — Snapshot types to types.ts (1 h, type-only)
  5. Candidate 3 — Game Registry (discuss first — ADR candidate)
