Architecture review

The slot-fill round family

Three daily games — Topothesies, Πόσο κάνει; and Λογοπαίγνιο — were each built by cloning the last. They now share a spine that nobody owns: the same reducer skeleton, the same round hook, the same decay score, copied three times with the game-specific parts threaded through by hand. This review asks where that copying is shallow duplication worth collapsing into a deep module, and where the differences are real enough to leave alone.

useSlotFillRound

Each game hands over its reducer + a state→snapshot map. One place to test the RESTORE / liveActed contract.

Problem

The spine is shallow and triplicated — the interface is three fields, the copied implementation is ~60 lines each, and the tricky part (liveActed never flips on RESTORE) has no single place to be verified.

Solution

One generic useSlotFillRound<S,A,G> owns reducer wiring, the liveActed ref, RESTORE plumbing and persistence. Each game passes its reducer, initial-state factory, and a state→snapshot selector.

Wins

  • ▸ leverage: one interface, three call sites
  • ▸ locality: liveActed/RESTORE bug fixed once
  • ▸ interface shrinks; spine absorbs the ceremony
  • ▸ game #4 (any slot-fill) is an adapter, not a paste
  • ▸ the contract becomes the test surface
  • ▸ deletion test: passes — complexity reappears ×3
Why not just use useGuessRound? It exists but fits the Wordle family (status: playing/won/lost, no liveActed getter). The slot-fill family is a genuinely different shape: derived stage + solved/failed/gaveUp + a hasLiveActed() getter feeding useLiveScorePost. This is a sibling spine, not a reuse of the existing one. Two families, two spines — each deep.

Candidate 2

Extract the single-stage reducer skeleton

Worth exploring
in-process pure — trivial to test

Files

  • src/games/posokanei/lib/posokaneiReducer.ts — 83 lines
  • src/games/logopaignio/lib/logopaignioReducer.ts — 74 lines
  • (topothesies reducer is two-stage — see note)

Before — same skeleton, two bodies

// posokanei                // logopaignio
GUESS:                     GUESS:
  stage!=guessing? return    stage!=guessing? return
  !isValid(n)? return        norm=="" ? return
  eval price → record        eval brand → record
  push, derive()             push, derive()
GIVE_UP:  ← identical       GIVE_UP:  ← identical
RESTORE:  ← identical       RESTORE:  ← identical
derive(): solved/failed/    derive(): solved/failed/
          stage  ← identical           stage  ← identical

Red = the only lines that differ: the validity test and the per-guess evaluation. Everything else is copied.

After — skeleton takes two functions

// shared: makeSingleStageReducer({
//   maxGuesses,
  evaluate: (input, target) => record | null,
// })  → returns {reducer, makeInitialState}

// posokanei adapter
evaluate = (n, t) =>
  isValid(n) ? evalPrice(n,t) : null

// logopaignio adapter
evaluate = (s, t) =>
  norm(s) ? evalBrand(s,t) : null
// null ⇒ no guess consumed (input noise)

null is the no-op signal both games already need. derive / GIVE_UP / RESTORE live in the skeleton.

Problem

Two reducers share an identical state machine (derive, GIVE_UP, RESTORE, the "invalid guess no-ops" rule) and differ only in one evaluate step — but the machine is duplicated, so a change to the shared rule touches every game.

Solution

A makeSingleStageReducer(evaluate, maxGuesses) factory returns the reducer + initial-state. Games supply only evaluate, returning a guess record or null for input noise.

Wins

  • ▸ locality: the no-op / derive rule lives once
  • ▸ leverage: state machine tested once, thoroughly
  • ▸ game logic reduces to one evaluate fn
  • ▸ pairs naturally with Candidate 1
Scope caveat. Only the single-stage reducers (posokanei, logopaignio) fit cleanly. Topothesies is two-stage (shape → capital) with its own transitions — force-fitting it into the skeleton would re-inflate the interface with stage-count config and hurt depth. Leave it out; two adapters (posokanei + logopaignio) already justify the seam, and a third slot-fill game would make it three.

Candidate 3

Collapse the guesses-left decay score

Speculative
in-process pure

Files

  • src/games/posokanei/lib/scoring.ts — 15 lines
  • src/games/logopaignio/lib/scoring.ts — 16 lines, identical logic

Before — two copies of one formula

// both files, verbatim except the
// config constant name:
if (!state.solved) return 0;
const wrong = guesses.length - 1;
return CFG.POINTS_PER_GUESS_LEFT
     * (CFG.MAX_GUESSES - wrong);

The only difference is POSOKANEI vs LOGOPAIGNIO.

After — one pure function, knobs passed in

// src/lib/decayScore.ts
export function guessesLeftScore(
  solved, guessCount,
  { pointsPerGuessLeft, maxGuesses },
) { ... }

// posokanei scoring.ts
guessesLeftScore(s.solved, s.guesses.length,
                 POSOKANEI)

Accepts its knobs (config-import stays at the call site, honouring the "never hardcode config" rule).

Problem

The decay formula is duplicated across two games. Low harm today — but it is the third copied artifact in the same trio, and the natural home for a shared "round scoring" vocabulary.

Solution

A pure guessesLeftScore(solved, count, knobs) in src/lib/. Each game's scoring.ts becomes a one-line call that still imports its own config row.

Wins

  • ▸ locality: one formula, one test table
  • ▸ leverage: accepts knobs, so any decay game reuses it
  • ▸ smallest of the three — do it alongside C1/C2
Honest read. A 4-line formula behind a function is a shallow module on its own — the deletion test barely passes. It earns its keep only as part of a deliberate "slot-fill round toolkit" (C1 + C2 + C3 together), not in isolation. Do not do this one alone.
🛑

Leave these alone — the differences are real

Not everything that looks parallel is shallow duplication. These earn their separate implementations.

  • shareText.ts Genuinely different. posokanei renders a variable-length proximity row (🟩/🟨/⬛ + ⬆️/⬇️); logopaignio renders a fixed MAX_GUESSES-wide grid (🟩/🟦/⬜). Same idea, incompatible layouts — merging would need a strategy param and deepen nothing.
  • evaluateGuess.ts The actual game. Price-band proximity vs accept-list brand matching are the domain — this is where the games should differ. Never merge.
  • selectDailyPuzzle.ts One-line divergence, already justified. Identical bar the sort key (date vs id). Could take a keyOf param, but at ~12 lines the duplication is cheaper than the seam. Borderline — fold in only if C1 lands and it's free.

Top recommendation

Start with Candidate 1 — the round spine.

It is the deepest win with the strongest precedent: the codebase already deepened the Wordle family this exact way (useGuessRound, useLiveScorePost), so the pattern is proven and blessed. Two near-byte-identical hooks plus a third that only differs in its snapshot fields is the clearest deletion-test pass in the codebase. Land C1, then fold in C2 (the reducer skeleton) and C3 (the decay score) as a single "slot-fill round toolkit" — they're cheap once the spine exists and pointless before it. Leave shareText and evaluateGuess per-game; that's where these games are supposed to diverge.

Naming note for the grilling phase: the slot-fill family has no term in CONTEXT.md yet. If a shared spine lands, it wants a name (candidate: slot-fill round — a daily one-target guess game with derived stage + give-up + liveActed). Adding that term is a side effect to do inline, not a blocker now.
