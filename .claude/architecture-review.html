Candidate #1

normalizeLetters lives in the wrong game

Strong

Files

src/games/leksokipos/lib/normalize.ts src/games/leksiarxeio/lib/letterState.ts src/lib/greeklish.ts

Problem

normalizeLetters() — lowercase, strip accents, convert final ς → σ — is platform-wide knowledge. Every game and every data pipeline needs it. But it lives inside src/games/leksokipos/lib/normalize.ts. Leksiarxeio already imports it across game boundaries, which is the tell: a platform-level concept has been housed in a game-specific module. Adding a 4th game means importing from a sibling game — a seam that leaks.

Deletion test: delete the module. Complexity reappears in every game, every data loader, every API route that touches words. It was earning its keep — but in the wrong place.

Solution

Move normalizeLetters to src/lib/normalize.ts (or co-locate with src/lib/greeklish.ts, which already handles Greek text transformation). Re-export from the old path with a deprecation note, then migrate all imports. The function is pure, small, and already tested — migration risk is near-zero.

Benefits

Locality: all Greek-text normalisation knowledge lives in one place — a future maintainer adding accent support knows exactly where to look. Leverage: any module (game lib, API route, CLI script) imports it without creating an inter-game dependency.

Candidate #2

ConnectionsLeaderboardModal rewrites instead of extending

Strong

Files

src/components/shared/LeaderboardModal.tsx src/components/leksindeseis/ConnectionsLeaderboardModal.tsx src/components/leksokipos/LeaderboardModal.tsx src/components/leksiarxeio/LeksiarxeioLeaderboardModal.tsx

Problem

LeaderboardModalBase (307 lines) provides a deep module: day-strip navigation, name editor with dirty-state guard, 5-minute polling + tab-visibility refresh, player-row separation in the table — all behind a small interface that Leksokipos and Leksiarxeio use successfully via slot props (topSlot, emptySlot, footerSlot).

Leksindeseis has a different Score format ("2/4 mistakes") so it discarded the base and rebuilt a parallel implementation (~165 lines) duplicating the modal shell, overlay, day-strip, name editor, and table. Two implementations, one concept. A bug fixed in the base won't reach Connections; a UI change to the day-strip requires two edits.

Deletion test: delete ConnectionsLeaderboardModal. Complexity concentrates in the base. That's the right shape.

Solution

Add a formatScore?: (raw: number) => string prop (and a scoreLabel prop already exists) to LeaderboardModalBase. Leksindeseis passes formatScore={n => `${n}/4`}. Then rewrite ConnectionsLeaderboardModal as a thin wrapper like the other two — ~20 lines of prop wiring instead of 165 lines of reimplementation.

Benefits

Locality: all leaderboard shell behaviour lives in one file. Leverage: the base becomes deeper — same interface, more games served. Adding a 4th game's leaderboard is ~20 lines, not 165.

Candidate #3

Score submission pipeline: five files for one concept

Strong

Files

src/hooks/useScoreSubmission.ts src/lib/postScore.ts src/app/api/game-scores/route.ts src/app/api/leksiarxeio-scores/route.ts src/lib/supabase.ts

Problem

To answer "can a Score be submitted twice for the same Puzzle?", a reader must trace five files: the hook guards with lastPostedRef (client-side deduplication); postScore is a 5-line fetch wrapper that silences errors; each API route validates fields; the Supabase upsert enforces a unique constraint (server-side deduplication). The deduplication logic is split between the hook and the database — the API route doesn't know about it.

postScore.ts is the clearest shallow module here: a 5-line function that serialises to JSON and ignores errors. It fails the deletion test — the two lines of actual behaviour (JSON body, ignore errors) reappear trivially at the call sites. It adds indirection without adding leverage.

Solution

Inline postScore into useScoreSubmission. Move the client-side deduplication guard (lastPostedRef) into a comment explaining why it exists alongside the upsert constraint. The concept "Score submission is idempotent at the DB level" should live in one file, not be implicit across three.

Benefits

Locality: the full submission path is readable in two files (hook + route) instead of five. Leverage: removing the shallow postScore layer eliminates a file that looks important but adds nothing — future readers won't have to decide whether it's meaningful.

Candidate #4

pickRandom7() business logic buried inside LetterPickerModal

Worth exploring

Files

src/components/shared/LetterPickerModal.tsx src/games/leksokipos/lib/

Problem

LetterPickerModal contains a 35-line pickRandom7() function that enforces Leksokipos Puzzle quality rules: center must be a vowel, at least one additional vowel in outer ring, at least two consonants. These are the same rules as the Pre-built Puzzle quality filters.

This logic is UI-component-internal. An API route or a test can't verify a player-submitted Custom Puzzle meets the same rules without copying the function. The quality contract is split: batch-generation has it in one place, interactive picking has it in another.

Deletion test: delete the component function. The 35 lines of quality rule logic reappear in the game lib — exactly where they belong.

Solution

Extract pickRandom7() and the quality predicate to src/games/leksokipos/lib/randomPuzzle.ts. The component imports and calls these functions. This makes the quality rules testable independently and usable in API routes validating Custom Puzzle URL parameters.

Benefits

Locality: all Leksokipos Puzzle quality rules live in the game lib alongside scoring, validation, and normalization. Leverage: a future feature (e.g., "suggest a random center letter" via API) can reuse the same picker without touching component code.

Candidate #5

GameBoard god component: orchestration tangled with render

Worth exploring

Files

src/components/leksokipos/GameBoard.tsx src/hooks/useScoreSubmission.ts src/hooks/useLeaderboard.ts src/hooks/useProfileVerification.ts src/hooks/useGameIdentity.ts src/games/leksokipos/hooks/useGameState.ts

Problem

GameBoard.tsx (~333 lines) calls five hooks and owns all side effects: game state, score submission on win, leaderboard open/close, profile linking, word-suggestion flow, keyboard wiring, and rendering all sub-components. The result is that understanding "what happens when the player wins?" requires reading GameBoard end-to-end — the effects are spread across useEffect blocks interspersed with render logic.

This isn't a shallow module — the implementation is genuinely complex. The problem is that two responsibilities (orchestration of side effects and rendering of sub-components) share the same file, so neither can be understood in isolation.

Solution

Extract a useGameOrchestration(puzzle, deviceId) hook that owns: composing the five sub-hooks, all useEffect side effects (score submission on win, Leaderboard refresh, profile verification trigger). GameBoard becomes a rendering shell that calls one hook and wires returned values to sub-components.

⚠ This is the largest refactor of the six. Worth doing if the team frequently needs to reason about Session win logic — but defer if GameBoard is rarely touched.

Benefits

Locality: all win/loss side effects live in one hook — readable in one screen. Leverage: the orchestration hook is testable without mounting a React tree (just call the hook in a test harness). The render layer is testable independently with a stub hook.

Candidate #6

useRoundPersistence: implicit shouldSave contract differs per game

Worth exploring

Files

src/hooks/useRoundPersistence.ts src/games/leksokipos/hooks/useGameState.ts src/games/leksiarxeio/hooks/useGameState.ts src/games/leksindeseis/hooks/

Problem

useRoundPersistence accepts an optional shouldSave? guard. Three games use it with different strategies:

  • Leksokipos — no guard passed (always persists immediately)
  • Leksiarxeio — shouldSave: snap => snap.guesses.length > 0 (only after first Guess)
  • Leksindeseis — no guard (trusts snapshot memoization)

It is unclear whether the Leksarxeio guard is an intentional design choice or an accidental omission elsewhere. Optional shouldSave makes the contract implicit — a developer adding a 4th game reads three examples and picks one, not understanding why they differ.

Solution

Make shouldSave required (not optional). This forces each game to explicitly state its persistence rule and document the rationale inline. For games with "always persist", the caller passes () => true — explicit intent, zero ambiguity. This is a small change with high documentation value.

Benefits

Locality: each game's persistence contract is visible at the call site. Leverage: the interface becomes self-documenting — shouldSave tells maintainers and TypeScript exactly when persistence fires.

Before — implicit optionality

useRoundPersistence(
  gameId,
  sessionKey,
  snapshot,
  onRestore,
  // shouldSave? — sometimes
  // present, sometimes not,
  // meaning unclear
)

After — explicit required guard

useRoundPersistence(
  gameId,
  sessionKey,
  snapshot,
  onRestore,
  shouldSave: () => true,
  // or:
  // snap => snap.guesses.length > 0
  // ← each game states intent
)

Top Recommendation

Start with #1 — normalizeLetters, then #2 — Connections leaderboard

Candidate #1 is a pure mechanical move: no behaviour changes, tests stay green, and it breaks an inter-game dependency that grows more painful with every new game. Candidate #2 has the highest ratio of duplication eliminated to code changed — ~145 lines of parallel-rewrite collapse into ~20 lines of prop wiring. Together they take under an hour and leave the codebase measurably deeper. Candidate #3 (inline postScore) pairs naturally with any work in the score submission area. The remaining three (#4–#6) are good targets once the team is in a refactoring mindset, but none is urgent.
