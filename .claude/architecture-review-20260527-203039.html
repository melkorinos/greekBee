Architecture Review

Single-candidate deep-dive: merging leksiarxeio_scores into game_scores

Strong candidate

Merge leksiarxeio_scores into game_scores

Files involved

src/app/api/leksiarxeio-scores/route.ts src/app/api/game-scores/route.ts src/hooks/useScoreSubmission.ts src/components/leksiarxeio/LeksiarxeioLeaderboardModal.tsx Supabase: game_scores table, leksiarxeio_scores table

Problem

Leksiarxeio has its own parallel infrastructure for a problem that game_scores already solves. useScoreSubmission explicitly excludes Leksiarxeio ("For Leksiarxeio use the other hook") — a seam smell. Two routes, two tables, two hooks, two leaderboard URL builders all exist because of one schema difference: Leksiarxeio stores 5 per-length rows instead of 1. But game_scores already has a data JSONB column sitting empty for all existing games — the store for that per-length breakdown already exists.

Before / After

BEFORE — two parallel stacks

Leksokipos · Leksindeseis

useScoreSubmission ↓ POST /api/game-scores ↓ game_scores table
score=integer, data={} ↓ GET /api/game-scores
ORDER BY score DESC

Leksiarxeio

submitLength() (separate) ↓ POST /api/leksiarxeio-scores ↓ leksiarxeio_scores table
5 rows/player/day ↓ GET /api/leksiarxeio-scores
aggregate 5 rows → total, ORDER BY total ASC

AFTER — one unified stack

useScoreSubmission
gameId: "leksiarxeio" | "leksokipos" | "leksindeseis" ↓ POST /api/game-scores
if leksiarxeio: read→patch data→recalc score→upsert
else: simple upsert ↓ game_scores table (one row/player/day/game)
score=total attempts, data={4:n,5:n,6:n,7:n,8:n} ↓ GET /api/game-scores
?sort=asc for leksiarxeio
leksiarxeio_scores table → dropped
POST /api/leksiarxeio-scores → dropped (or redirect)

Positives

  • + Locality: All leaderboard write logic lives in one route. A bug in score deduplication, cleanup, or RLS is fixed once, affects all games.
  • + data JSONB already exists and is unused ({}) for Leksokipos/Leksindeseis. Per-length breakdown slots in without a schema change.
  • + useScoreSubmission unification: The "use the other hook for Leksiarxeio" comment disappears. All three games share one hook, one contract.
  • + Future games cost zero: Any new game gets a leaderboard by passing its game_id. No new table, no new route, no new hook.
  • + One less table in Supabase = one less RLS policy, one less thing to migrate, one less thing to monitor.
  • + Leverage: The upsertAndClean shared helper, the 7-day rolling window, the "pin player row" GET pattern — Leksiarxeio gets all of this for free after the merge.

Negatives

  • − Sort direction branch: game_scores GET must handle score DESC (Leksokipos, Leksindeseis) and score ASC (Leksiarxeio) via a ?sort=asc param. Not complex, but it adds a conditional to a shared module.
  • − Read-modify-write on POST: Leksiarxeio posts one length at a time. Each POST must read the existing row's data, patch the new length in, recalculate the total, then upsert. This is a 2-step operation vs. the current simple upsert. Race conditions are theoretically possible (same player, two lengths posted simultaneously) but practically impossible.
  • − score column is semantically overloaded: Reading the DB directly, you need to know the game_id to interpret whether score=10 is good or bad. For Leksokipos 10 pts is a poor score; for Leksiarxeio 10 attempts is great. The column name becomes a lie for Leksiarxeio rows.
  • − Migration cost: Existing leksiarxeio_scores rows must be aggregated and inserted into game_scores before dropping the old table. If done wrong, players lose their historical leaderboard data.
  • − Test blast radius: Touching the shared game-scores route means any regression can affect Leksokipos and Leksindeseis leaderboards, not just Leksiarxeio — broader impact from a targeted change.
  • − Aggregation logic moves into the shared route: The "fill missing lengths with penalty=7, sum all 5" logic currently lives in leksiarxeio-scores GET and is easy to find. After the merge it's gated behind if (game_id === "leksiarxeio") inside a shared route — less obvious to a future reader.
Key question: Is the per-length aggregation logic inherent to Leksiarxeio's domain (in which case a separate seam is correct), or is it accidental implementation detail that the shared module should hide? The answer is accidental — the domain concept is still "a player's daily leaderboard score," just computed differently. The route's job is to hide that computation. That points toward the merge being architecturally sound.

Recommendation

Merge — but be deliberate about the two risks.
The unification wins (locality, leverage, hook simplification) clearly outweigh the costs. The two things to do carefully: (1) write the migration SQL precisely and verify row counts before dropping leksiarxeio_scores; (2) keep the aggregation logic in a named helper (aggregateLeksiarxeioScore(data)) inside the route rather than inline, so it stays findable. The sort-direction branch and read-modify-write are both small and contained.

What does NOT change

  • ✓ LeksiarxeioLeaderboardModal — only its buildUrl changes (points to /api/game-scores)
  • ✓ LeaderboardModalBase — untouched
  • ✓ useLeaderboard hook — untouched
  • ✓ All game logic (src/games/leksiarxeio/lib/) — untouched
  • ✓ Leksokipos and Leksindeseis leaderboard behaviour — identical to today

Migration SQL (to run in Supabase before deploying)

-- 1. Aggregate leksiarxeio_scores into game_scores (one row per player per day)
INSERT INTO game_scores (game_id, puzzle_date, device_id, display_name, score, data)
SELECT
  'leksiarxeio' AS game_id,
  puzzle_date,
  device_id,
  -- pick the most recent display_name for this player on this day
  (array_agg(display_name ORDER BY word_length DESC))[1] AS display_name,
  -- total attempts (missing lengths already penalised at write time in old table?
  -- if not: 35 - sum(attempts) won't work; use: sum(attempts) + (5 - count(*)) * 7)
  SUM(attempts) + (5 - COUNT(*)) * 7 AS score,
  jsonb_object_agg(word_length::text, attempts) AS data
FROM leksiarxeio_scores
GROUP BY puzzle_date, device_id
ON CONFLICT (game_id, device_id, puzzle_date)
DO UPDATE SET
  score = EXCLUDED.score,
  data  = EXCLUDED.data;

-- 2. Verify counts match before dropping
SELECT COUNT(DISTINCT (device_id, puzzle_date)) FROM leksiarxeio_scores;
SELECT COUNT(*) FROM game_scores WHERE game_id = 'leksiarxeio';

-- 3. Drop old table (run only after verifying counts)
-- DROP TABLE leksiarxeio_scores;
